# 单表知识模板（memory/tables/ 撰写规范）

> 本文件是 `memory/tables/` 下所有单表文档的撰写规范与模板。
> 文档命名 = 表名.md；每张表一份。doc_table.py 生成的草稿与本模板同构（草稿的语义部分留「待补充」）。

## 为什么是这个结构（设计意图）

单表文档是检索链的第二跳（overview → 单表详情 → SQL 片段 → sql_syntax）。
模型读完它要能独立写出正确 SQL，因此每一节对应模型写 SQL 时的一个决策点：

| 节 | 对应决策 | 缺了会怎样 |
|---|---|---|
| 用途 | 这张表是不是我要的表 | 选错表，全盘皆输 |
| 粒度 | 一行是什么、与别的表几对几 | 跨表聚合重复计算 |
| 时间字段 | WHERE 必须带什么过滤 | 全表扫、口径漂移 |
| 字段表 | SELECT 哪些列、WHERE 怎么写 | 选错字段、写错比较 |
| 指标口径 | 聚合公式怎么写 | 口径错——最致命的一类 |
| 注意事项/坑 | 哪些雷不能踩 | 踩团队已知踩过的坑 |
| 常用过滤 | 现成的 WHERE 片段 | 重复推导、口径不一致 |
| 关联键 | JOIN 用什么键 | 错关联、行数爆炸 |

## 撰写规则（合格标准）

1. **只写事实与已确认的口径**；推测必须标注「待确认」。宁缺毋假。
2. **坑 ≥ 3 条**，每条写成「现象 → 正确做法」；这一节是本文档的护城河。
3. **字段表覆盖全部字段**（doc_table.py 草稿已从 schema 生成），但含义/口径只对
   关键字段展开，无关字段可写「略」——禁止整行写「略」的字段留空含义列会误导模型。
4. **指标口径给公式**（SUM/COUNT + 过滤条件），不给形容词（「销售额」✗；「SUM(pay_amt) WHERE order_status<>'cancelled'」✓）。
5. 时间过滤字段必须写「所有查询必须带」——对应错误分类里的 PARTITION_ERROR 预防。
6. 关联键写明方向与语义，1:N 的那一侧必须提示「先聚合/去重再关联」。

## 模板（复制后替换 <> 内容）

# <表名> <中文名>

- 用途：<一句话：这张表回答什么业务问题>
- 粒度：一行 = <一个什么实体>；唯一键 <key>；与 <表名> 是 <1:N / N:1> 关系
- 时间字段：<字段>（<类型>，<覆盖范围>）；所有查询必须带该字段过滤。<跨天/口径归属等额外约定>
- 字段表：

| 字段 | 类型 | 含义 | 口径/取值 | 备注 |
|---|---|---|---|---|
| <字段名> | <类型> | <含义> | <取值或口径> | <备注> |

- 指标口径：
  - <指标名>：<公式>（<过滤条件>）
- 注意事项/坑：
  - <现象> → <正确做法>
- 常用过滤：
  - `<SQL 片段>`（<业务含义>）
- 关联键：
  - <本表字段> → <对方表>.<字段>（<关联语义>）
