# Phase 5 面试复盘：回归评测 Eval

> 本文档是面试话术底稿。Phase 5 把一次性验收（11 题测试 + 冷启动）固化成
> **可重复运行的回归评测集**——项目的质量保险层。全部事实有代码与实测记录支撑。

---

## 0. 电梯演讲（30 秒版）

> 我负责的 Phase 5 是回归评测：把前几轮跑通的 15 个业务场景固化成评测集，
> 用确定性校验器（不调 LLM）做三层检查——知识库覆盖是否完整、SQL 口径模式
> 是否符合规则、语法能否通过 EXPLAIN 验证，连"写操作必须被拒绝"都做成了
> 一条用例。验收做了两个破坏测试：故意写坏一条 SQL 被精确报出 1064 语法错、
> 故意删掉一份表知识被精确报出文件名。从此每次改提示词或知识库，跑一遍
> eval 就知道改坏了什么——提示词工作流有了工程化的回归保障。

**为什么这么开场**：钩子=破坏测试双通过（证明 eval 不是摆设）+ 确定性 grader（工程选择）。

## 1. Phase 5 在整盘棋里的位置

```
Phase 1-4  建成了：执行层 + 知识库 + 工作流 + 双自进化线

```

**怎么讲**：前四个 Phase 是"造出来"，Phase 5 是"守得住"——**自进化系统的最大风险不是
不会进化，是进化会退化**（模型写坏知识库、改 prompt 引入回归）。eval 就是守门员。

## 2. 核心设计理念

### 2.1 确定性 grader 优先（CS621 eval 经验迁移）

三层校验全部是确定性检查，不调 LLM：

| 层 | 查什么 | 抓住什么 |
|---|---|---|
| 知识覆盖 | 用例的表在 overview 有行、详情文档存在、指标有口径定义 | 知识库被删/退化 |
| SQL 规则 | must_have 命中 / must_not_have 零命中 | 口径规则被违反（去重漏了、过滤漏了） |
| EXPLAIN | dry-run 语法验证（不抓数据抓语法错） | 语法错误 |

**方法论：能写规则检查的，就不交给模型判断——确定性 grader 快、准、可解释、可重复。**

### 2.2 标准答案不用 agent 的输出（CS621 的直接教训）

15 个用例的参考 SQL 全部来自**独立跑通过**的测试（11 题迭代、冷启动会话、知识库片段）。
**不能让 agent 的结果当标准答案——那是自己判自己，评测就成了照镜子。**

### 2.3 把安全防线纳入回归

`case_write_reject`：`DELETE FROM orders` 交给 execute_query.py 执行，**断言被策略层拒绝
（PERMISSION_ERROR）**。只读防线（Phase 1 的白名单）从此也是回归保护对象——防线退化
（比如白名单被改松）会被 eval 抓住。

### 2.4 澄清/拒绝用例的特殊处理

`case_vague_question`（"最近表现怎么样"）无 SQL 检查——正确行为是**提问澄清**，
不是执行查询；eval 单独报告。**"无正确答案"的题也要进评测集**（行动方案设计）。

## 4. 决策档案（面试故事）

### 4.1 破坏测试：证明 eval 不是摆设

- **现场**：验收标准要求"对故意写坏的 SQL 和缺失的表知识，两类检查都能报出失败"。
- **实测**：SELEC 拼写错误 → EXPLAIN 精确报 1064 + 位置；products.md 改名 →
  知识覆盖报"缺详情文档 memory/tables/products.md"。
- **方法论：评测器本身要用破坏测试验收——会抓错的 eval 才可信。**

### 4.2 用例的「答案」从哪来

- **决策**：15 个参考 SQL 全部来自前几轮**实测跑通**的查询，不是现场新写。
- **方法论：回归用例 = 历史经验的固化。前几轮测试的价值不止于验收当刻，
  它们沉淀成用例后，价值变成永久的。**

### 4.3 reject 用例：安全防线的回归化

- **设计**：把 DELETE 语句放进评测集，断言 PERMISSION_ERROR。
- **意义**：Phase 1 的纵深防御（白名单/账户/只读事务）第一次有了自动验证。
  以后任何人改 execute_query.py 的安全逻辑，eval 都会说话。

### 4.4 与 11 题交叉对账的关系

11 题测试中的 5 处交叉对账（跨表上卷=单表直算等）是**正确性证据**；Phase 5 把它们
代表的**口径规则**（去重、过滤、上卷键）编码成 must_have 模式。**对账证明当时对，
模式保证以后不坏。**

## 5. 决策权衡清单

| # | 决策 | 为什么 | 面试一句话 |
|---|---|---|---|
| 1 | 确定性 grader 不调 LLM | 快、准、可解释、可重复 | "能写规则的不用模型" |
| 2 | 答案来自跑通的测试 | 防自己判自己 | "eval 不能照镜子" |
| 3 | 三层校验 | 知识退化与 SQL 违规是两类问题 | "知识库坏和 SQL 坏都要抓" |
| 4 | reject 用例 | 安全防线也要回归 | "防线退化必须可检测" |
| 5 | clarify 用例单独报告 | 无正确答案的题预期是提问 | "澄清也是正确行为" |
| 6 | EXPLAIN 而非正则验语法 | 真解析器比正则强一个量级 | "让数据库当裁判" |
| 7 | exit 1 | 回归失败必须可脚本化 | "能进 CI 的评测" |

## 6. 追问防御清单

1. **"15 个用例够吗？覆盖率怎么保证？"**
   → 15 个按四类分层设计：基础/口径陷阱/多步/澄清拒绝，覆盖了知识库里的核心坑
   （去重、自然期、跨天、NULL、歧义）和双自进化产物。且用例集是自进化的：
   SKILL.md Step 6 的"用例补充"会随新失败模式增长。**覆盖率靠分层设计 + 持续补充，
   不靠一次写满。**

2. **"eval 会不会误报（用例本身错了）？"**
   → 参考 SQL 全部实测跑通过（EXPLAIN + 执行），不是纸面 SQL；且每次 eval 跑 EXPLAIN
   复验。**用例自身的正确性由历史执行记录背书。**

3. **"为什么不加 LLM judge 评解读质量？"**
   → 行动方案预留了扩展位，但原则是确定性优先：解读质量是 Phase 3 冷启动验收过
   的维度，量化它的收益低、成本高、方差大。**CS621 原则：LLM judge 是最后手段，不是首选。**

4. **"eval 什么时候跑？"**
   → 每次改 SKILL.md 或知识库后；将来接入 CI。当前手动一键。**回归评测的价值在
   频率——改完就跑。**

5. **"自进化会改知识库，eval 怎么防止自进化改坏？"**
   → 两层：eval 的知识覆盖检查抓"文档被删/表被移出"；模型落库有人工闸门
   （Phase 4 已实现）。**自进化有闸门，退化有报警。**
