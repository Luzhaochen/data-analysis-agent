# Phase 1 面试复盘：确定性执行层

> 本文档是面试话术底稿，不是技术文档——每一节都回答"这段怎么讲、为什么这么讲"。
> 所有数字都来自 `runs/` 下的真实实验记录（retry_log），面试时引用它们比任何形容词都有说服力。

---

## 0. 电梯演讲（30 秒版）

> 我在做一个数据分析智能体，Claude Code 插件形态：用户用自然语言提问，它读业务知识库、生成 SQL、查询 MySQL、验证结果、最后把新知识写回知识库——核心价值在**知识库的自进化**。
>
> 我负责的是 Phase 1「确定性执行层」：agent 的手和眼。它不承担智能，只做三件事——**执行 SQL、拿元数据、把错误分类成可修复的建议**。设计哲学一句话：**程序负责确定性的事实，模型负责语义的判断**。
>
> 这一层我实测踩了三个有代表性的坑：MySQL 9 的错误码与文档不符、超时机制的假设被实验推翻、以及一个无法从协议层区分的"伞状"错误码的分类决策。

**为什么这么开场**：先给全景（知识库自进化是主线），再收窄到你的部分，最后预告三个故事钩子——面试官会顺着钩子问，主动权在你。

## 2. 核心设计理念（两个，都是追问弹药）

### 2.1 确定性脚本与语义决策分离

**是什么**：SQL 执行、元数据查询、错误分类是确定性脚本（Phase 1）；"用户想问什么、错了怎么改、结果怎么解读"是语义决策（Phase 3 的 SKILL.md 工作流）。

**为什么**：
- **可测试**：确定性层可以不依赖任何模型做回归评测（Phase 5 用已知答案对拍）；
- **可替换**：宿主模型可以是任何支持 Claude Code 协议的模型，执行层不感知模型是谁；
- **失败可归因**：出问题时能分清"脚本返回的事实错了"还是"模型判断错了"，不会一锅粥。

**一句话版本**：让程序做程序擅长的事（精确、可复现、留痕），让模型做模型擅长的事（模糊语义、权衡、解释）。

### 2.2 纵深防御（三层）+ 双层超时

**只读三层**（数据库安全，面试高频）：

| 层 | 机制 | 拦什么 |
|---|---|---|
| ① 代码层 | DENY 黑名单 + 文件读写模式拦截 | 明显的写语句，秒拦 |
| ② 账户层 | `data_agent` 账号仅 SELECT | 黑名单漏掉的写语句 → 报 1142 |
| ③ 会话层 | `SET SESSION TRANSACTION READ ONLY` | 防**误配了高权限账号**的写操作 → 报 1792 |

**为什么第③层存在**：前两层都假设"账号配置正确"。如果哪天 connection.ini 误填了 root，① 漏掉的写语句会把库写坏。会话级只读事务是"配置错误也安全"的最后防线。**一句话：每一层都假设上一层会失效。**

**双层超时**（稳定性设计）：

```
0s ───────── timeout_s(30s) ─────── read_timeout(35s)
                  │                        │
          max_execution_time        客户端 socket 兜底
          → 3024（明确：超时）      → 2013（模糊：见 §4.3）
```

- **服务端** `max_execution_time` 掐查询，信息明确（3024 = 就是超时）；
- **客户端** `read_timeout = timeout_s + 5` 留 5 秒余量，专门兜"服务端管不了"的场景（如执行很快但结果集传输慢——`max_execution_time` 只管执行阶段，管不了传输阶段）；
- **+5 秒的设计意图**：让信息更明确的一方先出手。两道超时不会同时触发。

## 3. 交付物逐个过（被问"你写了什么"时的回答顺序）

四个文件 + 一份配置，共约 1000 行。每个交付物背一句"职责一句话"，展开讲一个亮点就够。

### 3.1 `_lib/database_client.py`（共享客户端，~400 行）

**职责一句话**：统一建连、统一输出、统一错误包装——三个脚本共用的底座。

**关键部件**：

| 函数 | 做什么 | 亮点 |
|---|---|---|
| `load_analysis_config()` / `load_db_config()` | 每次调用**重新读文件** | 改 `config/analysis.json` 立即生效，不用重启任何东西 |
| `connect()` | 建连 + 会话初始化 | autocommit + DictCursor；建连即 `SET SESSION max_execution_time` 和只读事务；1045 认证失败翻译成中文可操作报错 |
| `fetch_rows()` | 执行 + 抓取 | `fetchmany(max_rows + 1)`——**+1 探针探测截断**（见 §4.4） |
| `to_jsonable()` / `to_display()` | 序列化 | Decimal 双轨策略：JSON 转 float（展示够用）、表格/CSV 保持字符串（**不丢精度**）；精确计算永远在 SQL 内完成 |
| `emit_json()` | 统一 JSON 输出 | 捕获 OSError——下游 `head` 截断管道时静默降级到 devnull，**绝不让 traceback 裸奔**（见 §4.6） |
| `classify_error()` | 错误码 → 分类 + 中文建议 | 四类可重试 + 三类基础设施（见 §3.2 表）；每个建议都是**可操作的下一步动作**，不是错误描述 |
| `render_table()` | 人读表格 | `east_asian_width` 把中文按双宽对齐——表格对齐这个细节是给"直接看终端输出"的人体验 |
| `append_retry_log()` | 尝试留痕 | JSON 读-改-写，损坏自动恢复，attempt 自增——**每次尝试（成功或失败）都留痕**，这是 Phase 4 自进化的数据源 |

**追问防御**：
- *为什么不用 ORM？* → 这里只需要执行与序列化，pymysql 足够；依赖少 = 安装分发（Phase 6）风险小。
- *为什么 Decimal 转 float？* → JSON 展示场景 <1e12 时 float 精度足够；**精确计算一律放在 SQL 内做**（ROUND/SUM），客户端不做计算，这是口径正确性的边界。
- *为什么错误建议写中文？* → 宿主模型的建议质量取决于提示词的针对性；中文建议直接可被模型复用为修复指令。

### 3.2 `skills/database-query/scripts/execute_query.py`（SQL 执行入口，291 行）

**职责一句话**：框架 Step 4 的执行器——安全检查 → 自动 LIMIT → 执行 → 错误分类 → 留痕。

**安全三态策略**（§4.5 的故事）：

| 输入 | 处理 |
|---|---|
| 非黑名单开头（select/with/explain/show/describe/desc 等只读词） | 放行给数据库执行 |
| DENY 列表写关键字（insert/update/delete/…，含 repair/check 等维护语句与 INTO OUTFILE 模式检测） | 秒拦 → PERMISSION_ERROR |
| 未知关键字（如拼错的 `SELEC`） | **转发给数据库**，让它报真实的 1064 |

**其他亮点**：
- **多语句检测**：状态机解析器，引号和注释感知（不会把字符串里的 `;` 误判为语句分隔）；
- **自动 LIMIT + 探针**：无 LIMIT 追加 `max_rows + 1`；显式 LIMIT 超过硬上限时**压回** `hard + 1`（`clamp_explicit_limit`）；正则还处理了 `LIMIT n OFFSET m` 和尾行注释；
- **`--dry-run`**：把查询包成 `EXPLAIN FORMAT=TRADITIONAL` 返回执行计划——**改 SQL 前先看它走什么索引**，这是 Phase 5 回归评测的工具基础；
- **三种输出**：JSON（给模型）、CSV（给后续处理）、表格（给人看）；CSV 模式 meta 走 stderr，数据流纯 stdout 可直接管道；
- **最后兜底**：`except Exception → UNKNOWN_ERROR`——**任何未预期的异常都变成结构化 JSON**，traceback 永不裸奔。

### 3.3 `get_metadata.py`（元数据，135 行）

**职责一句话**：模型"记不清表结构"时，拿 information_schema 的真实 schema 喂给它。

- 表/字段/索引三个查询；`build_indexes()` 把 STATISTICS 行分组还原成"索引 → 列序列"；
- `--brief` 输出概述种子（表名/注释/近似行数/列数）——这是 **Phase 2 知识库的启动原料**；
- **诚实的估算**：`approx_rows` 如实标注为 InnoDB 估算值。为什么这是亮点？因为 agent 用错数据源做决策比没有数据更糟——**标注不确定性本身就是设计**。

### 3.4 `doc_table.py`（建档骨架，149 行）

**职责一句话**：把 schema COMMENT 自动转成表文档**草稿**——机器填事实，语义留白。

- DRAFT_TEMPLATE 里字段名/类型/COMMENT/主键/时间候选自动填充；业务语义（"这个字段在什么场景下用"）标记 `待补充`；
- **草稿只进 `runs/drafts/`，绝不直接写 memory**——因为"该不该沉淀为知识"是语义判断，属于 Agent 的活，不属于脚本；
- 这是 Phase 2"知识库构建"的机械化部分：**人工审阅是知识质量的闸门**。

### 3.5 错误分类表（整个 Phase 1 的"产品功能"）

**四类可重试 + 三类基础设施**，每个错误码都实测过（映射表在 `database_client.py` 顶部注释）：

| 分类 | 触发示例 | 应对 | 可重试？ |
|---|---|---|---|
| PARTITION_ERROR | 日期值格式错（1525/1292）、分区越界（1526） | 检查时间过滤写法、确认字段类型 | ✅ |
| FIELD_ERROR | 字段不存在（1054）、表不存在（1146）、列歧义（1052） | 调 get_metadata 拿真实 schema | ✅ |
| SYNTAX_ERROR | 语法错（1064）、ONLY_FULL_GROUP_BY（1055）、标量子查询多行（1242） | 对照 memory/sql_syntax.md | ✅ |
| PERMISSION_ERROR | 权限拒绝（1142/1144/1145/1227）、只读拒绝（1792） | 明确告知，不重试 | ❌ |
| CONFIG_ERROR | 配置缺失/损坏 | 修复配置 | ❌ |
| CONNECTION_ERROR | 连不上（2003/2006）、连接中断 | 检查服务与网络 | ❌ |
| TIMEOUT_ERROR | 服务端超时（3024）、连接中断（2013，见 §4.3） | 缩小范围/先聚合 | ✅ |

**分类设计的本质**：错误分类不是给用户看的，是给**重试循环**看的——每一类对应"要不要重试、重试前改什么"。这就是为什么 PERMISSION 不重试（改了也没用）、FIELD 要拿 metadata（不改 schema 认知重试还是错）。

## 4. 试错档案（面试最值钱的部分）

**叙事节奏模板**（每个故事都套这个弧线）：
> **假设 → 设计实验 → 实测 → 发现推翻/证实 → 修正 → 提炼方法论**

面试官问"项目里最难的 bug 是什么"，从下面挑一个讲。**每个故事都要落到一句方法论**——那才是你的东西。

### 4.1 1525：文档说 1292，MySQL 9 说 1525

- **现场**：`WHERE order_dt > 'abc'` 报 1525，进了 UNKNOWN_ERROR（分类表按 MySQL 8 文档写的是 1292）。
- **修正**：把 1525 补进 1292 分支，并按 message 细分日期/非日期（日期 → PARTITION_ERROR）。
- **方法论：错误分类表不能抄文档，必须实测校验。** 服务器版本不同，错误码会漂移——映射表的可信度来自"每个条目都亲手触发过"。这条已写进代码注释，Phase 5 会为每个分类建回归用例。

### 4.2 SLEEP 免疫假说被实验推翻（最完整的"假设被推翻"故事）

- **假设**：按 MySQL 文档印象，注释里写了"SLEEP() 不受 max_execution_time 限制"。第一次实验 `SLEEP(31)`（上限 30s）跑了 30.05 秒后成功返回——被我**误读**为"自然睡完，果然免疫"。
- **怀疑**：当时没看 SLEEP 的**返回值**。
- **决定性实验**（config-lab）：把 `timeout_s` 压到 5，跑 `SLEEP(8)` 和 `SLEEP(15)`——两者都在 **5.05 秒**返回，返回值 **1**。
- **真相**：MySQL 里 SLEEP 返回值有约定——**0 = 睡满，1 = 被打断**。max_execution_time 每次都掐断了 SLEEP，31 秒那次也是被打断的。且被掐断的语句以**成功**结束（返回 OK），不产生 3024；真正报 3024 的是跑不动的行处理查询（大 CROSS JOIN 聚合，实测 30053ms 精确命中）。
- **修正**：推翻注释、修正认知，并把"返回值语义"这个发现记进注释。
- **方法论**：**读实验结果的每个字段**——一个返回值差点骗过两次实验；**测试假设与确认假设同等重要**，主动构造能推翻自己的用例。

### 4.3 2013 伞状码：KILL 实验与分类决策（面试王牌故事）

- **背景**：`read_timeout` 兜底理论上会报 2013，但从未实测过（本地传输太快，自然触发不了）。
- **实验设计**：后台挂起 `SLEEP(1000)` 长查询，临时把 `timeout_s` 调到 120 开操作窗口（**且 120 秒处服务端兜底会打断它，实验失败也不会挂死**——实验设计自带双保险），让 root 在 Workbench 里 `KILL <连接id>` 制造"查询中连接丢失"。
- **结果**：112 秒处 KILL 生效 → 客户端收到 2013 "Lost connection to MySQL server during query" → 分类走了 TIMEOUT 分支。但建议文案说"查询超过 120s 被中断"——**真实原因是连接被杀，文案说谎了**。
- **发现**：2013 是"伞状"错误码——超时兜底、KILL、断网**同码同文案**，MySQL 协议层不给客户端任何区分手段。
- **决策**：三个方向的权衡（详见 §5），最终选了"文案中性化"：分类仍归 TIMEOUT（可重试），但建议如实列出两种可能，最终判定交给 SKILL.md 工作流。
- **方法论**：**错误码是伞状分布，客户端无法 100% 分类时——按先验概率 + 错误成本决策，把不确定性显式写进建议交给上层**。这个故事能一次性展示：实验设计能力（可复现、有兜底）、诚实（主动暴露自己代码的说谎）、权衡能力（成本分析）。

### 4.4 LIMIT 探针失效：探测机制必须与限制机制在同一层

- **现场**：`--limit 2` 返回 `truncated: false`——截断探测失灵。
- **根因**：SQL 内的 LIMIT 是**服务器端**限制，结果集到客户端时已被截成 2 行；客户端的 `fetchmany(max_rows + 1)` 只能看到 2 行，探不到截断。
- **修正**：把 `max_rows + 1` **写进 SQL 内部**（`LIMIT max_rows + 1`），服务器多返回 1 行探针，客户端据此判断截断，探针行丢弃不展示。
- **方法论**：**探测机制必须与限制机制作用在同一层**——服务器端限制就要服务器端探测。

### 4.5 "SELEC" 白名单误伤：黑名单三态策略的由来

- **现场**：拼写错误的 `SELEC` 被白名单拦下，分类成了 PERMISSION_ERROR——把"语法错误"误诊成"权限问题"，修复路径全错。
- **根因**：第一版设计把所有非白名单开头都拦，误伤了拼写错误这类"该让数据库诊断"的输入。
- **修正**：三态策略——DENY 列表秒拦、**未知关键字转发给数据库**报真实 1064、安全由账户权限 + 只读事务两层兜住。
  > 2026-09-20 补正（同事静态审查）：第一版的 READONLY_KEYWORDS 白名单常量在最终实现中零引用——"白名单放行"与"未知转发"实为同一分支（非黑名单即放行），常量已删除。当前策略层只有黑名单 + 文件读写模式检测，本条目按代码现状改写。
- **方法论**：**防御层的职责边界要想清楚**——策略层只拦"确定是坏的"，不确定的交给我后面更深的防御层。拦截不该以牺牲诊断质量为代价。

### 4.6 BrokenPipe：traceback 裸奔事故

- **现场**：输出被管道截断（`| head -c 400`）时，BrokenPipeError 的 traceback 直接喷了出来——违反"绝不让 traceback 裸奔给模型看"的铁律。
- **修正**：`emit_json()` 捕获 OSError，把 stdout 重定向到 devnull 静默降级。
- **方法论**：**约束要覆盖所有输出路径**——正常路径之外的边界（下游提前关闭管道）也得兜住。

### 4.7 测试用例设计的两个教训

- **教训一（优化器短路）**：想验证 3024 超时，先用了 `COUNT(*) CROSS JOIN`——446ms 就完成了，优化器把笛卡尔积的计数短路了。换成真正做行处理的 `GROUP BY` 聚合才在 30053ms 精确命中 3024。
- **教训二（边界竞态）**：第一版超时实验用 `SLEEP(10)`，而当时 `read_timeout = 10`——两个定时器精确撞在同一时刻，结果取决于竞态。拆成 `SLEEP(8)`（服务端掐）和 `SLEEP(15)`（服务端掐）两个**确定性**用例。
- **方法论**：**测试要选真实病灶**（绕开优化器的"聪明"），**用例设计要避开边界竞态**（每个用例只有一个确定的预期结果）。

### 4.8 验收全记录（数字弹药库）

`runs/phase1-check/retry_log.json` 16 条尝试是完整的"错误 → 修正"轨迹，面试时可引用：

- 4 类错误分类全部实测通过（1054 / 1064 / 1525 / 1142 + 策略层拦截）；
- 3024 超时精确 30053ms；SLEEP 打断 5046.6 / 5048.9ms 返回 1；
- KILL 实验 112140ms 收到 2013（runs/kill-lab）；
- LIMIT 6 重写与 truncated 标志（runs/config-lab）。

## 6. 追问防御清单（面试高频追问 + 回答要点）

1. **"为什么不用 embedding RAG 做知识检索？"**
   → 知识库是结构化 Markdown（表知识/片段/规则），量级在几十个文件；顺序阅读工作流（检索链）可解释、可调试、零额外依赖。embedding 的收益在知识库到几千条后才显现，现在引入是过度设计。**可解释性对 agent 调试的价值 > 检索效率的价值。**

2. **"为什么重试循环不在脚本里？"**
   → 重试上限、每次重试改什么，是语义决策（"这个错误该不该重试"依赖上下文），属于 Phase 3 工作流。脚本只做"每次尝试记录 attempt"。分层原则：**确定性层做事实，语义层做决策**。强行前置会让脚本承担模型的工作。

3. **"max_execution_time 和 read_timeout 会不会互相打架？"**
   → 不会，有 +5s 余量保证先后：服务端 30s 先出手（3024），客户端 35s 兜底（2013）。且实测 SLEEP 被服务端掐断后语句成功结束，客户端根本没等到超时。唯一重叠场景（服务端管不了的传输阶段）正是 read_timeout 存在的意义。

4. **"2013 万一真是超时，归 TIMEOUT 但文案说'也可能是被终止'，模型会不会选错？"**
   → 这正是设计意图：模型看到两种可能后，按 SKILL.md 工作流先检查"查询是否明显过重"再决定路径。**确定性层不替模型做它才有资格做的判断**。退一步讲，两条路径的第一步都是"重试"（重试新建连接），选错路径的代价接近零。

5. **"为什么 Decimal 转 float，不怕精度问题吗？"**
   → JSON 展示场景 <1e12 时 float 精确到分足够；**任何精确计算都在 SQL 内做**（SUM/ROUND），客户端只展示。表格/CSV 输出走 `to_display` 保持 Decimal 字符串原样，一分钱不丢。

6. **"策略层被绕过怎么办？"**
   → 策略层只是第一层。绕过它（比如注释混淆）后面还有账户 SELECT-only（1142）和只读事务（1792）。三层实测验证过：刻意绕过策略层的写语句在数据库层被拒。**防御设计的前提是每一层都可能被绕过。**

7. **"错误分类表会不会漏错误码？"**
   → 会，所以 UNKNOWN_ERROR 的建议是"把该错误码补进映射表"——分类表是**自进化的**。Phase 2 知识库的 sql_syntax.md 会沉淀新码，Phase 4 会从 retry_log 统计未知码。承认会漏 + 设计好补漏路径，比假装全覆盖诚实。

8. **"这层跟 LLM 有什么关系？没有模型它不也能跑？"**
   → 对，它本来就不该依赖模型——这是故意为之：执行层是 agent 的**可靠基座**，模型负责的是它上面的语义层。可靠的东西不能有概率。类比：人类的肌肉反射不需要意识参与，但意识指挥肌肉。
