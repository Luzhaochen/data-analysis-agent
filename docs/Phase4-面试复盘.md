# Phase 4 面试复盘：Hooks 自进化兜底

> 本文档是面试话术底稿。Phase 4 把专业人士指导的**自进化途径①（会话结束 hook 触发更新）**
> 落成代码，与途径②（团队空间扫描）一起构成完整的自进化闭环。
> 全部事实有代码（hooks/）、踩坑笔记（hooks/DEBUG.md）与端到端实测记录支撑。

## 0. 电梯演讲（30 秒版）

> 我负责的 Phase 4 是自进化的兜底机制：会话结束时 Claude Code 自动触发我的钩子脚本，
> 把会话信息入队；下次会话开始时自动处理——统计这次会话真正查询了哪些表、把使用频次
> 累加进知识库索引、给没建档的表生成草稿，并把进化摘要注入新会话。
> 开发中最有价值的发现是钩子协议的约束塑造了架构：SessionEnd 事件只有 1.5 秒预算，
> 所以我设计成「散场入队、开场干活」的队列化方案；以及一个语义教训——「表名出现过」
> 不等于「表被使用」，计数必须匹配 SQL 的 FROM/JOIN 子句。最终验收时，两条自进化线
> 并行协作：模型按工作流自己把留白表 refunds 完整建档落库，钩子同时把计数 +1。

**为什么这么开场**：三个钩子——协议约束塑造架构（1.5s 队列化）、语义陷阱（出现≠使用）、两条线并行协作。面试官会问"两条线怎么分工"。

## 2. 核心设计理念

### 2.1 协议约束塑造架构：1.5 秒预算 → 队列化设计

动手前先派专项 agent 查证 Claude Code 官方 hooks 协议（**接口规则是对方定的，只能查不能编**），
发现 SessionEnd 事件只有 **1.5 秒共享预算**——而我们要干的活（解析逐字稿、计数、建档）要好几秒。

设计：**散场只入队，开场干重活**——

```
会话 A 结束 ──→ SessionEnd 钩子（毫秒级）：把 session_id/transcript_path 追加进队列
会话 B 开始 ──→ SessionStart 钩子（600s 预算）：消费队列 → 计数 → 建档 → 幂等记录
                                          → stdout 进化摘要注入新会话上下文
```

**方法论：先查协议预算再定架构——约束不是麻烦，是设计的输入。**

### 2.2 两条自进化线：语义归模型，确定性归脚本

| 线 | 谁 | 干什么 | 用户可见？ |
|---|---|---|---|
| 语义线 | 模型（SKILL.md Step 6） | 判断"该不该沉淀"、写文档/片段、审阅落库 | 可见（"本会话已沉淀"） |
| 确定性线 | 钩子脚本 | 使用计数、草稿骨架、队列/幂等 | 不可见（摘要注入模型上下文） |

端到端验收时两条线在 overview 的**同一行上并行协作**：模型把 refunds 行从"⏳ 未建档"改写成正式链接，钩子把使用频次 0→1。**分工边界：语义判断归模型，机械计数归脚本**——与 Phase 3 的分层原则一脉相承。

### 2.3 容错哲学：宁可少计数，不可崩钩子

- transcript 是官方不承诺稳定的内部格式 → 文件缺失/坏行一律跳过；
- 建档走子进程，失败只记日志不影响计数；
- 钩子任何异常都不阻塞 Claude Code 本身（exit 0 兜底）。

## 4. 决策档案（面试故事）

### 4.1 1.5 秒预算：协议查证直接改变了方案

- **现场**：行动方案原设计"SessionEnd 里解析 transcript + 计数 + 建档"，查协议发现 SessionEnd 只有 1.5 秒共享预算。
- **决策**：队列化——散场入队（毫秒级）、开场干活（600s 预算）。
- **方法论：动手前先查对方接口的约束；协议细节决定架构，不查就踩坑。**

### 4.2 计数语义陷阱：「出现」≠「使用」（本 Phase 最有价值的坑）

- **现场**：第一版按"表名出现在逐字稿"计数，实测 9 张表**全部 +1**。
- **根因**：模型读 overview.md 时，文件全文进了逐字稿——索引表格里 9 个表名全"出现"。
- **修正**：只匹配 SQL 的 `FROM/JOIN` 子句。知识库索引不命中 FROM，只有真实查询命中。
- **方法论：计数前先定义"什么行为算使用"——语义定义错误会让数据全部失真。**

### 4.3 配置只在会话启动时加载

- **现场**：当前会话里改 settings.json，钩子静默不触发，一度以为没注册成功。
- **排查结论**：配置在会话启动时加载。**钩子没跑先问一句"当前会话加载的是哪版配置"。**

### 4.4 低级 bug 的教训：本地模拟 stdin 测试

- **现场**：`set |= list` 类型错误——本地管道模拟 stdin 一秒钟就炸出来，比等真实会话触发快得多。
- **方法论：钩子的每个逻辑分支都能用一条管道本地测，不要等真实事件。**

### 4.5 端到端验收：refunds 留白表的完整闭环

- **现场**：让真实会话问"退款原因分布"（逼模型用留白表 refunds）。
- **结果**：模型按 Step 6 独立落库 refunds.md——**实测驱动**（精确定位生成器埋的 3 条脏数据、金额 35,337.11 元）、诚实标注验证范围；同时钩子计数 +1、state 记录、零报错。
- **两条线并行的活证据**：模型改文档内容，钩子改计数——互不干扰、各自分工。

### 4.6 摘要注入"看不到"的真相

- **现场**：用户观察"第二次会话开场没看到 [自进化] 摘要"，一度以为钩子没跑。
- **真相**：SessionStart 钩子的 stdout 是**注入给模型的内部上下文，用户界面不显示**——证据（state/计数/队列消费）证明钩子确实干了活。验证注入靠问模型"你开场收到了什么系统消息"。
- **方法论：钩子的反馈渠道分两种——给模型的（上下文注入）和给证据的（日志/文件），排查先看证据文件。**

## 6. 追问防御清单

1. **"SessionEnd 为什么不直接干活？"**
   → 官方协议：SessionEnd 只有 1.5 秒共享预算。解析逐字稿+计数+建档要好几秒。所以散场只入队、开场干重活——**这是读协议读出来的设计，不是拍脑袋**。

2. **"两条自进化线会不会重复干活/打架？"**
   → 分工明确：模型负责语义（写文档、判断口径），钩子负责确定性（计数、草稿骨架、幂等）。实测它们在 overview 同一行上各改各的字段，互不冲突。**重叠的是目标，不重叠的是动作。**

3. **"钩子崩了会不会把会话搞挂？"**
   → 不会。协议规定 exit 1 只是非阻塞错误；我们的设计进一步保证：全程 try/except + exit 0 兜底，任何异常只进日志。**兜底机制必须比主流程更稳。**

4. **"transcript 格式官方不承诺稳定，你不怕吗？"**
   → 怕，所以容错：解析失败=少计数，不崩钩子。且计数只依赖最通用的 SQL 语法（FROM/JOIN 正则），不依赖 JSONL 具体字段结构。**对不稳定的依赖，用最薄的接口。**

5. **"为什么钩子里不调 LLM？"**
   → 钩子是确定性兜底，语义判断归会话内的模型（Step 6）。钩子里调 LLM 会引入成本、延迟和新的失败面，且 Claude Code 官方不推荐在钩子里派生子进程 agent（防循环）。**确定性的事让脚本干。**

6. **"使用频次计数的业务价值是什么？"**
   → overview 是检索链第一跳，频次是"哪些表是团队高频资产"的客观数据：长期高频表值得维护更好、零频次表值得核查是否过时。**知识库也需要使用数据来管理自己。**
