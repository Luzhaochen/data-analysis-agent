## 2. 核心设计理念

### 2.1 junction 指针方案：一箭双雕

skills 安装用 Windows junction（链接）而不是复制：

```
~/.claude/skills/analysis → (junction) → D:\data-analysis-agent\skills\analysis
```

两个收益：① **改仓库代码即时生效**，永不出现"装了一份旧版"；② **顺带解决路径问题**——
脚本里 `parents[3]` 找仓库根，junction 的路径解析跟随链接回到真实位置，
config/memory/runs 照常可用。如果复制，路径解析会断。**Phase 1 埋的路径伏笔，
Phase 6 兑现。**

### 2.2 JSON 合并不覆盖（框架「保留已有配置」要求）

hooks 合并进用户级 settings.json：**读入 → 只改 hooks 键 → 备份后写回**。
用户已有的 env/permissions/theme 等配置原样保留（实测验证：卸载后 env 配置
完好）。**安装脚本的第一原则：不动用户已有的东西。**

### 2.3 幂等与卸载边界

- 安装跑两遍零变化零报错（junction 已存在跳过、hooks 已注册跳过）；
- 卸载只删**自己建的东西**：junction 和 hooks 键；connection.ini（含用户填的密码）
  与 runs/ 数据保留——**卸载不是格式化，是退出。**

### 2.4 开发期项目级 / 分发期用户级

Phase 4 开发时用项目级注册（`.claude/settings.json`，可提交、clone 即用）；
Phase 6 安装后统一由用户级承载。**过渡状态必须清理**——这是双注册教训的总结。

## 4. 决策档案（面试故事）

### 4.1 双注册并发：安装验证抓到的最值钱 bug

- **现场**：装完用户级后做端到端验证，hook.log 出现"state/queue 写入失败"——但
  数据是对的（orders 计数只 +1、state 无重复）。
- **根因**：用户级 + 项目级都注册了 SessionStart 钩子 → 开场时两个进程**并发**
  抢写 state 文件/删队列 → 一个撞上"文件被占用/已删除"。
- **两层处理**：① 幂等兜底**保住了数据**（state 防重 + 入队去重——Phase 4 的双层
  幂等在真实并发下经受住了考验）；② 根因修复——项目级 hooks 退役（过渡状态清理），
  并发源消失。
- **方法论：防御设计兜住数据，根因修复消灭噪音——两层都要做，且顺序不能反。**

### 4.2 用户级 settings 没有项目占位符

- **发现**：`${CLAUDE_PROJECT_DIR}` 占位符只对项目级配置有意义，用户级 settings
  必须写绝对路径。
- **处理**：install.ps1 运行时用脚本自身位置推导仓库根，生成绝对路径写入。
- **方法论：配置模板的变量域要分清——占位符的作用域和配置的作用域一致。**

### 4.3 备份策略：只备份一次，保留最初原版

- **设计**：`settings.json.bak-datagent` 只在**首次修改前**创建（已存在不覆盖）——
  无论装多少次，备份里永远是用户最初的原版，卸载恢复有据。
- **方法论：备份的语义是"原版快照"，不是"上次状态"——覆盖备份会丢原版。**

### 4.4 卸载的边界意识

- **设计**：卸载删 junction 和 hooks 键；connection.ini（用户填了密码）和
  runs/（历史数据）不动。
- **方法论：卸载脚本要明确"什么是你的、什么不是"——只删自己装的，是卸载
  与破坏的分界线。**

## 6. 追问防御清单

1. **"为什么用 junction 不用复制？"**
   → 复制有两个坏处：改代码要重装（分发旧版风险）、脚本的仓库根解析会断
   （junction 的路径解析跟随链接回到真实位置）。**指针方案同时解决了分发
   新鲜度和路径正确性两个问题。**

2. **"双注册的并发冲突，你的幂等是怎么兜住的？"**
   → 两层：入队去重（同 session 只入队一次）+ 处理去重（state 记录已处理）。
   实测并发下 orders 计数只 +1 不重复。但兜底只是让数据对，日志噪音和竞态
   窗口还在——所以又做了根因修复（项目级退役）。**防御保数据，修复消根因。**

3. **"卸载为什么不删 connection.ini 和 runs？"**
   → connection.ini 里有用户填的密码，runs 是用户的分析历史。卸载脚本的原则
   是"只删自己装的"，这两个是**用户的数据**不是插件的数据。**边界意识：卸载
   与破坏之间就是这条线。**

4. **"安装脚本跨机器能用吗？"**
   → 依赖项都推导自脚本位置：仓库根 = 脚本所在目录、Python = 仓库 .venv。
   唯一前提是目标机器装过依赖（README 快速开始覆盖）。**配置里的路径全部
   运行时推导，不写死。**

5. **"为什么不用 install.sh 也写一个？"**
   → Windows 原生场景用 PowerShell 覆盖；项目运行环境就是 Windows + pwsh。
   跨平台版本是 Future Work（README 可标注）——**v1 覆盖真实场景，不为
   想象中的场景写代码。**
