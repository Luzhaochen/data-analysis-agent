# Phase 2 面试复盘：知识库构建与自进化

> 本文档是面试话术底稿，不是技术文档。Phase 2 是整个项目的**叙事主线**——
> 专业人士的判断：「agent 好不好用，核心在 memory 知识库」。
> 所有事实都来自仓库里可查的文件与实测记录。

---

## 0. 电梯演讲（30 秒版）

> 我负责的 Phase 2 是知识库——这个 agent 的灵魂。我把团队常用的 7 张表、每个字段的口径、
> 每张表踩过的坑、跑通的 SQL 片段和 SQL 语法规则，沉淀成结构化的 Markdown 知识。
> 每一节知识都对应模型写 SQL 时的一个决策点：用途对应选表、粒度对应防重复计算、
> 坑对应避雷。同时知识库是自进化的：业务方把新表 DDL 丢进团队空间，扫描脚本自动发现、
> 建档、人工审阅后落库——我完整演示了这个闭环，包括幂等和"表还没上线"的时序处理。

**为什么这么开场**：直接呼应"知识库是核心"的行业判断，然后给三个钩子：结构设计（8 节）、自进化（扫描闭环）、工程细节（幂等/时序）。

## 1. Phase 2 在整盘棋里的位置

```
Phase 0  模拟数据（可复现、带已知答案）                    ✅
Phase 1  确定性执行层（执行/元数据/错误分类）——agent 的手   ✅
Phase 2  知识库（表知识/片段/规则 + 自进化）——agent 的大脑  ✅ ← 本文档
Phase 3  主编排 SKILL.md（提示词工作流）——agent 的思维
Phase 4  Hooks 自进化兜底（会话结束沉淀）
Phase 5  回归评测
Phase 6  安装分发
Phase 7  打磨与面试包装
```

**怎么讲**：Phase 1 是"手"（能执行、能报错），Phase 2 是"大脑"（知道表在哪、口径是什么、坑有哪些）。没有 Phase 2，Phase 3 的模型再聪明也是"力气大的外行"；有了 Phase 2，普通模型也能表现得像熟练员工——**这正回应了专业人士的判断：决定 agent 上限的是知识库，不是模型**。

## 2. 核心设计理念

### 2.1 知识库格式 = 产品设计

知识库不是"资料的堆放"，格式本身就是产品。单表模板的 **8 节，每一节对应模型写 SQL 时的一个决策点**：

| 节 | 对应决策 | 缺了会怎样 |
|---|---|---|
| 用途 | 这张表是不是我要的表 | 选错表 |
| 粒度 | 一行是什么、几对几 | 跨表重复计算 |
| 时间字段 | WHERE 带什么过滤 | 全表扫、口径漂移 |
| 字段表 | SELECT 哪些列 | 选错字段 |
| 指标口径 | 聚合公式怎么写 | 口径错（最致命） |
| 注意事项/坑 | 哪些雷不能踩 | 踩已知的坑 |
| 常用过滤 | 现成 WHERE 片段 | 重复推导 |
| 关联键 | JOIN 用什么键 | 错关联 |

**一句话**：模板不是文档规范，是**给模型看的协议**——按协议填的知识，模型才能稳定消费。

### 2.2 知识库四件套的分工

| 件 | 回答 | 类比 |
|---|---|---|
| overview.md | 去哪张表找什么 | 目录 |
| tables/*.md | 这张表怎么用、口径是什么、坑在哪 | 每台设备的说明书 |
| sql_snippets/ | 这类分析怎么查（现成 SQL） | 老师傅的配方 |
| sql_syntax.md | 通用规则（日期/聚合/去重/性能） | 车间安全规程 |

检索链：overview → 单表详情 → 片段 → 语法规则。**先宽后窄、先索引后细节**——模型按这个顺序读，是"带着问题找答案"，不是"把文档全读一遍"。

### 2.3 三条质量铁律

1. **只沉淀跑通的 SQL**——片段入库前必须实测（两个示范片段都实跑验证过）；
2. **口径给公式不给形容词**——写 `SUM(pay_amt) WHERE order_status<>'cancelled'`，不写"销售额"；
3. **坑 ≥ 3 条，每条 = 现象 → 正确做法**——坑是"能力不亚于真实员工"的来源：真实员工脑子里就是这些。

### 2.4 自进化：两条途径（专业人士指导的完整落地）

| 途径 | 触发 | 状态 |
|---|---|---|
| ① 会话中用户提供新表 | 会话结束 hook 触发建档 | Phase 4 |
| ② 定时扫描团队空间 | 业务方丢 DDL → scan_tables.py 发现建档 | **Phase 2 已落地并演示** |

## 3. 交付物逐个过

### 3.1 memory/tables/模板.md —— 撰写规范 + 草稿模板（单一事实源）

一份文件两用：上半部分是人读的撰写规范（8 节 + 6 条合格标准），下半部分是**机器渲染的草稿模板**（HTML 注释标记围住）。doc_table.py 读标记段生成草稿——**改模板不用改代码**（实测验证过：模板加一行，草稿跟着变）。内置兜底模板保证模板文件缺失时工具不罢工。

### 3.2 memory/tables/ —— overview + 7 张正式表（2 张故意留白）

- overview：一屏内的表索引 + 跨表口径速查；使用频次列预留给 Phase 4 hook 累加；
- 7 张表：orders（对账/渠道/促销口径）、order_items（行级金额 + 脏数据剔除）、products（挂牌价≠成交价）、categories（层级混存的上卷）、users（注册≠活跃、等级快照）、promo_calendar（区间重叠禁止日期 JOIN）、inventory（扫描演示落库）；
- **refunds / traffic 故意不建档**——留给自进化演示：agent 第一次遇到时触发草稿建档，形成"知识库从薄到厚"的可见进化曲线（这是 Phase 7 demo 的素材）。

### 3.3 memory/sql_syntax.md —— 双用途规则手册

- **事前预防**（检索链最后一跳）：模型生成 SQL 前读它，知道该带什么过滤、用什么口径；
- **事后修复**：报 SYNTAX/FIELD/PARTITION 错误时按错误码查对应小节（与 Phase 1 的错误分类建议互相指向）。
- 每条规则给 ✓/✗ 对照写法，防呆。

### 3.4 memory/sql_snippets/ —— 实测跑通的片段

2 个示范：每日 GMV 趋势（含自然期/促销期拆分）、促销效果对比（先聚合再 JOIN + 日均口径）。**实测的意外收获**：促销效果片段跑出了"B 级高频低效"的业务结论——知识库片段 = 可复现的分析能力，这就是"能力不亚于真实员工"的执行版。

### 3.5 doc_table.py 模板化（改造）

硬编码草稿模板 → 读模板.md 标记段渲染；顺带提取 `fetch_table()` 供扫描脚本复用。三验收：草稿与模板同构、改模板不用改代码、模板缺失兜底不阻塞。

### 3.6 hooks/scan_tables.py + mock_data/team_space/ —— 自进化途径②

扫描团队空间 *.sql 提取表名 → 过滤已处理（state）与已建档（overview）→ 查 information_schema：已上线生成草稿、未上线标记 pending_online → 输出汇总 + next_steps。**幂等双保险**：state 文件 + overview 解析两层过滤（实测：删掉 state 重扫，overview 依然拦住）。

## 4. 决策档案（面试故事，按叙事弧线组织）

> 每个故事：**冲突 → 决策 → 验证 → 方法论一句话**。

### 4.1 小维度表"没东西可写"——"无"也是信息

- **冲突**：categories 只有 4 个字段 13 行，模板八节大半没内容。
- **决策**：把"无"写成信息——时间字段：无（说明过滤在事实表侧）；指标口径：无（**禁止**在维度表上聚合）。坑从"**怎么被误用**"里挖：一级二级混存一张表、事实表挂的是二级、按名称分组会混层——三条坑全部指向真实会犯的错。
- **方法论：维度表的坑在"使用方式"里，不在脏数据里；写坑时自问"agent 用这张表会在哪一步踩雷"。**

### 4.2 挂牌价 ≠ 成交价（草稿 review 的典型）

- **冲突**：products 的 list_price 容易被模型当销售额用。
- **决策**：字段表里显式写"标价，**非成交价**"；坑 1 写清"成交价在 order_items.price"；指标口径写"list_price 禁止当金额参与聚合"。
- **方法论：最危险的错误是"看起来对"——口径类字段必须写明"不是什么"，不只写"是什么"。**

### 4.3 DDL 为什么只是"新表信号"

- **冲突**：扫描建档时，直接从团队空间的 DDL 解析 schema 更省事。
- **决策**：DDL 只用于"发现表名"，schema 事实源仍走数据库 information_schema。因为 DDL 文件与数据库实际结构可能漂移（业务方改了表没更新文件）——正是同事在 #1/#2 发现的同款漂移病根。
- **方法论：一个事实只允许一个源头；信号可以多路，事实必须单一。**

### 4.4 幂等双保险（实测支撑）

- **冲突**：定时扫描反复跑是常态，重复建档会污染知识库。
- **决策**：两层过滤——runs/scan_state.json（已处理）+ overview.md 解析（已建档）。实测：删除 state 后重扫，overview 层依然拦住（新表数 = 0）。
- **方法论：幂等不能靠"记得别跑两次"，要靠状态文件；关键状态值得两层防御。**

### 4.5 pending_online：真实世界的时序

- **冲突**：业务方可能先丢 DDL、后建表。
- **决策**：扫描发现表名但库中不存在 → 标记 pending_online，不建档**也不写 state**（下次继续等），不报错。
- **方法论：处理真实世界的时序问题，比假设"一切都按顺序发生"值钱得多。**

### 4.6 片段实测跑出业务结论

- **现场**：促销效果片段跑通后，S 级日均 482.7 万 vs B 级日均 60~227 万——"B 级高频低效"从文档形容词变成查询结果。
- **方法论：知识库片段的价值 = 把分析能力沉淀成可复用的查询；片段入库前实测，是知识可信度的底线。**

### 4.7 人工闸门：机器发现，语义归 Agent

- **决策**：scan 只生成草稿（runs/drafts/），落库 memory/tables/ + 更新 overview 由主 Agent 审阅后做。
- **方法论：机器负责确定性发现，语义判断（这表该不该进知识库）归 Agent——分层原则贯穿全项目。**

## 6. 追问防御清单

1. **"为什么不用 embedding RAG？"**
   → 知识库是结构化 Markdown，量级几十个文件；顺序阅读检索链可解释、可调试、零额外依赖。embedding 的收益要知识库到几千条才显现。**对 agent 调试而言，可解释性 > 检索效率**。且渐进披露：overview 先定位，只读相关文档，省上下文。

2. **"知识库会不会膨胀失控？"**
   → 三道约束：模板强制八节结构（防注水）；overview 保持一屏内（入口不膨胀）；使用频次计数（Phase 4 hook 累加，长期不用的表文档会被发现）。**格式约束 + 入口约束 + 数据约束**。

3. **"为什么故意留 2 张表不写？"**
   → 自进化需要被看见。留白让"第一次遇到 refunds → 草稿建档 → 审阅落库"成为可演示的闭环。全写满了，自进化机制就没有舞台。**这也是 demo 的叙事需要。**

4. **"DDL 都拿到手了，为什么还要查数据库？"**
   → 漂移。业务方改表结构不一定同步 DDL 文件——同事审查时就在 schema.sql 和 alter_promo.sql 之间发现过同款漂移。**事实源单一化是血泪教训驱动的设计。**

5. **"scan 发现新表为什么不直接进知识库？"**
   → 语义判断归 Agent：这张表该不该进知识库、字段口径怎么定，机器做不了。机器生成草稿、人审阅落库——**质量门槛高于进化速度**（这也是自进化不被污染的关键）。

6. **"知识库是中文写的，模型能稳定消费吗？"**
   → 宿主模型 DeepSeek 对中文指令与文档理解没有障碍，且团队真实使用场景就是中文业务口径。**知识库语言 = 团队工作语言**，这本身就是"贴合团队"的设计。

7. **"坑从哪来的？"**
   → 三个来源：schema 设计时埋的口径教学点（channel 历史 NULL、促销区间重叠）、脏数据注入（price 漂移）、真实项目经验迁移（duration_days 字符串混入来自真实 DataWorks 导出数据）。**每个坑都有出处，不是编的。**

8. **"这些知识库文件，模型怎么保证读完？"**
   → Phase 3 的 SKILL.md 把"按检索链读知识库"设为硬性前置步骤（未读 overview 不得生成 SQL）；sql_syntax.md 是生成前的最后一跳。**知识库写得再好，也要工作流强制消费——这是 Phase 3 的活。**
