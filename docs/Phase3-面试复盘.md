## 0. 电梯演讲（30 秒版）

> 我负责的 Phase 3 是 agent 的思维层：把数据分析工作流编码成提示词——意图解析、知识检索、
> SQL 生成、执行重试、结果校验、解读与自进化六步，外加 5 条硬性规则和每步自检清单。
> 验收做了两层：11 道真实业务题的迭代测试全部通过，其中 5 处独立查询的交叉对账分毫不差；
> 再做冷启动验证——新会话、无上下文，模型只靠我写的技能文件和知识库，7 项行为清单全过、
> 数字与标准答案一致，并且它主动把跑通的 SQL 沉淀进了知识库——**首次由模型独立完成的自进化**。

**为什么这么开场**：三个钩子——编码方式（规则+清单防跳步）、量化验收（11 题+交叉对账）、冷启动自进化（叙事高潮）。面试官会顺着"自进化"问下去。

## 2. 核心设计理念

### 2.1 硬性规则（5 条，违反即失败）

1. 未读 overview 不得生成 SQL；
2. 五要素不全必须先澄清；
3. **展示 SQL 与口径、用户确认后才执行**；
4. 事实以知识库与 get_metadata 为准，不凭记忆；
5. 环境只读。

**设计逻辑**：大模型在长工作流中会跳步。与其写 100 条"建议"，不如写 5 条"不得"——把最容易出事故的五个点变成硬边界，其余交给自检清单。

### 2.2 每步自检清单（防跳步第二道防线）

每一步结尾给 checkbox（"□ 读过 overview？□ 关联键没猜？"）。模型自问自答的成本极低，但能显著降低跳步率。**硬性规则管"不能做错的事"，自检清单管"容易漏做的事"。**

### 2.3 指针原则：SKILL.md 零重复知识库内容

SKILL.md 只写流程与指针（"去哪读"），表口径/语法规则全部在 memory/。两处漂移的老毛病（同事在 Phase 0 就抓到过 schema 与 alter 漂移）不犯第三次。**知识库是事实源，工作流是流程——分家。**

### 2.4 口径管理：默认推进 + 显式确认

业务词（"已完成"、"GMV"）存在多口径时：不无限追问，也不静默猜测——**用团队默认口径执行，展示 SQL 时说明口径并询问**。知识库侧则是多口径并存（每个口径有名字/公式/场景/默认标记）+ 行业参考写进坑（淘宝严格 completed 口径）。

### 3.1 skills/analysis/SKILL.md（主工作流，~130 行）

| Step | 内容 | 与下层衔接 |

## 4. 决策档案（面试故事）

### 4.1 「已完成」歧义 → 多口径体系（测试喂出来的设计）

- **现场**：第 1 题"已完成订单"触发了口径歧义——严格 completed vs 常规 `<> cancelled`。
- **转折**：用户反馈淘宝用严格口径。设计升级：知识库从"单一公式"改为**多口径并存**（默认标记 + 行业参考入坑），SKILL.md 加"默认推进 + 展示时询问"规则。
- **方法论：口径不是唯一正确答案，是可管理的集合——命名、公式、场景、默认值四要素。**

### 4.2 traffic schema 漂移（"不凭记忆"规则的实证）

- **现场**：题 7 涉及留白表 traffic，查 information_schema 发现实际字段是 `cart_cnt`，而方案设计文档里记的是 `visit_amt`。
- **方法论：设计文档会漂移，数据库不会——字段永远以 get_metadata 为准。** 这也正是"硬性规则 4"存在的原因。

### 4.3 模糊题的澄清行为（题 11）

- **现场**："最近平台的转化表现怎么样？"——五要素三缺。agent 没有瞎猜也没有拒绝，而是**列出缺失要素 + 给出基于知识库的默认建议**（指标=下单转化率/时间=近 30 天/维度=整体+分品类），用户一句"按默认建议"即可推进。
- **方法论：澄清的体验设计——不要让用户填空，让用户做选择题。**

### 4.4 11 题交叉对账（量化验收的核心手段）

5 处独立查询结果互相印证、分毫不差：

| 对账对 | 结果 |
|---|---|
| 跨表上卷 GMV（题6'）= 单表直算（题1） | 313,192,219.05 = 313,192,219.05 |
| 月度累计 H1（题8）= 渠道分组合计（题3） | 565,248,914.67 两处一致 |
| 自然期同比（题10②）= 自然期 CTE（题5） | 228,460,111.79 / 32,321 一致 |
| 分品类订单合计（题11）= 整体订单（题11） | 10,459 = 10,459 |

**方法论：SQL 正确性不能靠"看着对"，要靠独立路径交叉对账。这是把 CS621 eval 思想迁移到 SQL 场景。**

### 4.5 冷启动验证（最终验收）

新会话、无项目上下文，模型只有技能文件+知识库+工具。7 项行为清单全过，数字与标准答案分毫不差。三个超额表现：
- **五查拦截**：发现 6→7 月腰斩后先查数据缺天，验证完整才下结论；
- **错误自愈**：写错字段名（promo_level）→ FIELD_ERROR → 按标准应对查 schema → 修正 → 成功；
- **结构效应洞察**：拆出 618 大促效应（6/1-18 日均 960 单 vs 6/19 后 330 单），提出"订单降幅>流量降幅"的效率分析。

### 4.6 首次由模型独立完成的自进化（项目叙事高潮）

冷启动会话结束时，agent **主动询问**"跑通的 SQL 是否有复用价值、要我沉淀吗"；用户同意后，它独立完成：按片段规范入库（双写法：整月对比 + 促销/自然期矩阵）、同步 traffic.md 口径、同步 overview.md。**全部实测跑通**。而写法二产出了比原问题更深的答案：整月转化率下降是**结构效应**（促销期 0.16→0.15、自然期 0.09→0.11，同口径未恶化）。

**这个故事串起了整个项目：P1 的机制 + P2 的知识 + P3 的工作流 = 一次真实的"知识库随业务进化"。**

### 4.7 pymysql 版本反转（诚实复盘素材）

requirements.txt 被改三次：同事猜 1.1.1 → 我用 `pymysql.__version__` 改 2.2.8 → 同事查 PyPI 改 1.2.0（正确）。根因：`__version__` 属性返回 2.2.8 是上游打包的内部编号，**判断 pip 版本要看 PyPI/pip 元数据**。
**方法论：又一个"假设被实测推翻"——查版本要查权威源；且敢于承认自己错了，协作中的版本冲突以权威源定胜负。**

| # | 决策 | 为什么 | 面试一句话 |

| 1 | 5 条硬性规则 | 长工作流跳步是模型常态，规则要少而硬 | "5 条『不得』比 100 条『建议』有效" |

## 6. 追问防御清单

1. **"为什么用提示词工作流，不微调模型？"**
   → 工作流可审查、可迭代、可版本管理；微调在这个规模是过度设计。且宿主模型可替换（Claude Code 插件形态），工作流与模型解耦。**失败的提示词可以改一行修复，微调失败的模型要重训。**

2. **"硬性规则会不会限制模型发挥？"**
   → 硬规则只覆盖"出错代价最高"的五件事（检索、澄清、确认、事实源、只读），其余全部留给模型判断。**边界内自由，边界外禁止**——这恰恰是给模型发挥空间的框架。

3. **"每次执行都要用户确认，不烦吗？"**
   → 数据分析场景里，口径错误比等待更贵。且确认是一次性的（用户说"确认"即可），换来的是**口径可追溯**。展示内容=SQL+口径表，用户审的是口径不是代码。

4. **"怎么证明提示词改对了？"**
   → 11 题迭代测试 + 5 处交叉对账 + 冷启动验证。改 SKILL.md 后重跑测试集，回归对比。**提示词是代码，要有测试**（这是 Phase 5 eval 的雏形）。

5. **"模型写坏知识库怎么办？"**
   → 三道闸：只沉淀跑通的 SQL（实测要求）、更新前告知用户、人工可审阅（git 版本管理可回滚）。**质量门槛高于进化速度。**

6. **"冷启动验证一次就能说明稳定吗？"**
   → 不能，所以 Phase 5 会做 15 例回归评测集，且每次改 prompt 都回归。冷启动验证证明的是"机制链路通"，回归评测保证的是"持续不坏"。
