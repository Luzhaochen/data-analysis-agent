# 用户研究材料包（CS619 课程项目评估用）

两个小研究，全部纸面可跑，各约 15–20 分钟，2–3 名参与者即可。
**参与者是同学即可，不需要业务知识**：两个研究测的都是「说法 vs 参考材料」的一致性核查能力，
不是业务判断——《知识库摘录》是全部事实来源。这也正是真实场景（新同事核查 agent 输出）。
材料基于真实知识库与真实数据构造；**答案键在仓库外私有目录**（data-analysis-agent-eval-private/user_study_keys.md），勿让参与者看到。

## 研究 1（claim 1）：来源引用能否帮用户发现口径错误？

**研究问题**：分析输出中给每条口径标注知识来源，是否降低用户的核查成本（发现更多错误）？
**设计**：被试内 + 交叉平衡。两个任务（A：Q2 GMV；B：Q1 退款率），每个任务含 4 条口径说明、其中 2 条有错。一份材料带来源引用、另一份不带。参与者各做两个任务、两种条件各一次：

| 参与者 | 材料 | 条件 |
|---|---|---|
| 1 | packet1.md | A 带引用 / B 不带引用 |
| 2 | packet2.md | A 不带引用 / B 带引用 |
| 3 | packet1.md | 与参与者 1 相同 |

**流程**（15 分钟/人，含摘录页）：
1. 发材料 + 《知识库摘录》（claim1/excerpt.md）
2. 说任务（照 week6 think-aloud 规范，**中性措辞、不引导**）：
   「你是团队的数据同事。请像平时核查口径一样，审这两份分析输出：
   标记你认为有错误的口径说明并写一句原因，可以随时查摘录。做的时候说出你在想什么。」
3. 计时（每人每任务记起止时间）
4. 收回答题纸，当场不问"对不对"；答后可以简短访谈（哪条最可疑？查了什么？）

**收集的数据**：每任务命中数（找出真错误 0–2）、误报数、用时、出声记录（如做）。
**分析**：按条件汇总命中率（带引用 vs 不带引用）与用时；误报数单独报告。
**报告写法示例**：「N=2–3，被试内设计。带来源引用条件下 2 条埋入错误平均命中 X/Y，不带引用 Z/Y……」

## 研究 2（claim 2b）：用户能否有效地给记忆提案把关？

**研究问题**：Step 6 的提案格式（要记什么/内容预览/为什么/来源）能否让用户有效拦截错误更新？
**设计**：6 条记忆提案（3 真 3 假，错误类型各不相同：概念性错误 / 细节错误 / 写反），参与者逐条裁决：确认 / 修改 / 拒绝。
**材料**：claim2b/proposals.md（单页）+ 同一份《知识库摘录》（claim1/excerpt.md，参与者可对照核查）。
**流程**（15 分钟/人）：
1. 发材料，说任务：「会话结束时助手会提议把学到的东西写进知识库。请你对每条提案裁决：
   照写、修改后写、还是拒绝。写一句理由最好。可以对照《知识库摘录》查提案内容是否与记载一致。」
2. 不限时但计时；可出声思考。
**收集的数据**：错误提案被拦截数（拒绝或修改）、正确提案被放行数（确认）、理由原文。
**分析**：拦截率 = 错误提案被正确处理比例；放行率 = 正确提案被确认比例；理由做定性归类。
**预期洞察（写报告用）**：提案②（GMV 再扣退款）需要一点业务含义理解，新手参与者可能放过它——
若发生，这本身是发现：提案的「来源」字段应附带**可直接核对的原文段落**，否则非业务用户无法有效把关。
这类"没拦住 → 提出设计改进"的结论正是课程想要的 insights。
**报告写法示例**：「3 条埋入错误全部被参与者拒绝或修改（N=2–3）；参与者给出的理由显示其判断依据是内容预览与'为什么记'……」

## 如果找不到参与者怎么办

报告里如实写评估方式（设计 + 预演），把未执行的用户研究作为「设计讨论」呈现——课程允许 2–3 人小样本，也接受设计深度讨论。最低限度：你自己做一遍两个研究（自测），结果标注为单参与者的试点（pilot, n=1），仍比没有强。

## 与 e2e 自动化评测的关系

- 研究 1、2 测的是**人**（claim 1、2 的"用户"半边）
- claim 2 的"准确率"半边由 e2e 用例 004（退款率 before/after）测
- 两者合起来才是完整的 claim 2：**人拦得住错更新（研究 2）＋ 批准的更新提升查询准确率（e2e 004）**
